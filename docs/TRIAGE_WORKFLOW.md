<![CDATA[# 🔍 Alert Triage & Detection Tuning Workflow

This document describes the methodology used to triage alerts generated by simulated attacks, classify them as true or false positives, and iteratively tune detection rules.

---

## Triage Methodology

### Alert Classification Framework

Each alert is classified using a standardized scale:

| Classification | Code | Description |
|---|---|---|
| **True Positive** | TP | Alert correctly identifies malicious or simulated attack activity |
| **Benign True Positive** | BTP | Alert fires on legitimate activity that matches the rule but is not malicious |
| **False Positive** | FP | Alert fires on activity that does not match the intent of the rule |
| **False Negative** | FN | An attack occurs but the rule does not fire |

### Triage Decision Tree

```
Alert Fires
  │
  ├── Is the activity malicious or simulated attack?
  │     ├── YES → True Positive (TP)
  │     │     └── Document in Incident Report
  │     │
  │     └── NO → Is the activity expected/authorized?
  │           ├── YES → Benign True Positive (BTP)
  │           │     └── Consider whitelist or threshold adjustment
  │           │
  │           └── NO → False Positive (FP)
  │                 └── Root cause analysis → Tune the rule
  │
  └── Attack occurs but no alert
        └── False Negative (FN)
              └── Gap analysis → New or updated rule needed
```

## Triage Procedure (Per Alert)

### Step 1: Initial Assessment (2 minutes)

- Review alert name, severity, and MITRE mapping
- Note the timestamp and affected endpoint
- Check if this matches a scheduled attack simulation

### Step 2: Context Gathering (5 minutes)

Run the following Splunk searches to build context:

**Process context (Windows)**:
```spl
index=sysmon EventCode=1 Computer="<hostname>" 
| table _time, User, Image, ParentImage, CommandLine
| sort -_time
| head 20
```

**Authentication context**:
```spl
index=wineventlog EventCode IN (4624, 4625) ComputerName="<hostname>"
| table _time, EventCode, Account_Name, Source_Network_Address, Logon_Type
| sort -_time
| head 20
```

**Network context**:
```spl
index=sysmon EventCode=3 Computer="<hostname>"
| table _time, User, Image, DestinationIp, DestinationPort
| sort -_time
| head 20
```

### Step 3: Verdict & Documentation (3 minutes)

- Classify the alert (TP / BTP / FP / FN)
- If TP: Create incident report from template
- If FP/BTP: Log in `tuning/false_positive_log.md`
- If FN: Document the gap and create/update rule

## Detection Tuning Process

### Tuning Triggers

| Trigger | Action |
|---|---|
| FP rate > 20% for a rule | Mandatory tuning review |
| BTP from system accounts | Add whitelist for known-good processes |
| FN discovered during testing | Rule logic update or new rule creation |
| Threshold too sensitive | Adjust count/time window |

### Tuning Strategies

#### 1. Whitelist Known-Good Activity

```spl
# Before tuning (high FP from Windows Update)
index=sysmon EventCode=1 Image="*\\powershell.exe" CommandLine="*-EncodedCommand*"

# After tuning (exclude Windows Update)
index=sysmon EventCode=1 Image="*\\powershell.exe" CommandLine="*-EncodedCommand*"
  NOT (ParentImage="*\\svchost.exe" User="NT AUTHORITY\\SYSTEM" CommandLine="*WindowsUpdate*")
```

#### 2. Adjust Thresholds

```spl
# Before tuning (too sensitive — alerts on 3 failures)
index=wineventlog EventCode=4625 | stats count by src_ip | where count > 3

# After tuning (realistic threshold)
index=wineventlog EventCode=4625 | stats count by src_ip | where count > 10
```

#### 3. Add Process Ancestry Checks

```spl
# Before tuning (any schtasks.exe alerts)
index=sysmon EventCode=1 Image="*\\schtasks.exe"

# After tuning (exclude legitimate parent processes)
index=sysmon EventCode=1 Image="*\\schtasks.exe"
  NOT (ParentImage IN ("*\\services.exe", "*\\taskeng.exe", "*\\wmiprvse.exe"))
```

#### 4. Time-Based Filtering

```spl
# Exclude business hours for certain detections
... | where NOT (date_hour >= 9 AND date_hour <= 17 AND date_wday IN ("monday","tuesday","wednesday","thursday","friday"))
```

## Tuning Metrics

Track these metrics to measure detection quality:

| Metric | Formula | Target |
|---|---|---|
| Precision | TP / (TP + FP) | > 90% |
| Recall | TP / (TP + FN) | > 95% |
| FP Rate | FP / Total Alerts | < 10% |
| Mean Time to Triage | Average time from alert → classification | < 10 min |

### Lab Results Summary

| Rule | Pre-Tuning FP Rate | Post-Tuning FP Rate | Tuning Actions |
|---|---|---|---|
| T1110 Brute Force | 25% | 5% | Raised threshold 5→10, excluded service accounts |

| T1003.001 LSASS Access | 30% | 5% | Filtered Windows Defender, AV processes |
| T1548.002 UAC Bypass | 20% | 5% | Added registry path specificity |

## Escalation Criteria

Escalate an alert if any of the following apply:

- [ ] Activity originates from an unexpected source IP
- [ ] Multiple MITRE techniques observed from the same host within 30 minutes
- [ ] Credential dumping or lateral movement detected
- [ ] Persistence mechanism established
- [ ] Data exfiltration indicators present
